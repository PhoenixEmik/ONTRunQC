# Benchmarking

## Measurements in this environment

Measured on 2026-10-16 with the release build, Rust 1.98.1, macOS arm64, default
system allocator, and local files. Each row represents one timed execution;
these are observations, not throughput guarantees. No real research records or
identifiers are included in this repository.

| Input | Size (bytes) | Records | Wall (s) | User CPU (s) | System CPU (s) | Peak RSS (MiB) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Supplied PromethION fixture | 366,182 | 1,000 | 0.3866 | 0.006550 | 0.009275 | 2.61 |
| Synthetic scale test | 1,599,749,860 | 30,549,981 | 8.7736 | 8.525951 | 0.236408 | 476.30 |

Peak RSS in bytes: 2,736,128 for the fixture; 499,433,472 for the synthetic run.

The supplied `promethion_fixture.tsv` contains 999 basecalled reads, one
zero-length row, and 4,714,853 bp of yield. An independent Python `csv`/`statistics`
calculation matched overall counts, exact length median/N50, quality statistics,
channel/mux/reason counts and yields, both histograms, and cumulative time-bin
yield. The fixture is too small for a meaningful throughput estimate; startup and
filesystem effects dominate its elapsed time.

The scale input is entirely synthetic, with a repeated 1,000-row pattern of
varying read lengths, Q-scores, channels, muxes, filtering, reasons, and unsorted
start times. All 30,549,981 records are basecalled, exercising full storage of both
length and Q-score vectors. Total yield (473,081,441,871 bp), exact N50, both
medians, and mean quality were independently checked using weighted pattern
counts. Repeated executions generated byte-identical reports.

This synthetic input is repetitive and substantially smaller than the real
approximately 11 GB file. It exercises the target record count and memory path,
but does not establish performance on real PromethION data. The full
`sequencing_summary_PBM96073_e70444ee_4b72c09a.txt` was not available in this
environment. Benchmark it on the actual HPC system before claiming the
below-512-MiB real-run RSS target is met.

macOS `/usr/bin/time -v` is unavailable; `/usr/bin/time -l` could not finish
resource reporting because `sysctl kern.clockrate` was restricted. The table
uses Python `time.perf_counter()` around a checked `subprocess.run`, and
`resource.getrusage(resource.RUSAGE_CHILDREN)` in a fresh Python process for each
execution. On macOS `ru_maxrss` is bytes; Linux reports KiB. Resource accounting
does not include the Python parent. Memory and wall-clock results depend on the
allocator, filesystem/cache state, and competing workloads.

## Full-run procedure on Linux/HPC

Use a dedicated CPU and sufficient memory to observe rather than terminate runs
that exceed the target. Record CPU model, RAM allocation, filesystem/storage,
Rust/compiler version, build revision, and whether the input was already cached.
Use release mode and the committed lockfile:

```sh
cargo build --release --locked
mkdir -p benchmark-results
summary_path=/path/to/sequencing_summary_PBM96073_e70444ee_4b72c09a.txt
wc -c < "$summary_path" > benchmark-results/input-bytes.txt
rustc --version > benchmark-results/rust-version.txt
uname -a > benchmark-results/system.txt
/usr/bin/time -v -o benchmark-results/time.txt \
  target/release/poregauge analyze "$summary_path" \
  --output benchmark-results/qc/
```

The GNU time output includes elapsed wall time, user CPU, system CPU, and maximum
resident set size in KiB. Preserve the exit status and inspect errors before
using any previous report. Validate the current report:

```sh
python3 - <<'PY'
import json
from pathlib import Path
r = json.loads(Path('benchmark-results/qc/report.json').read_text())
m = r['metrics']
assert m['total_records'] == 30_549_981
assert m['basecalled_reads'] <= m['total_records']
assert m['passed_reads'] <= m['basecalled_reads']
assert m['passed_yield_bp'] <= m['total_yield_bp']
assert m['basecalled_reads'] + m['zero_length_records'] == m['total_records']
assert m['passed_reads'] + m['failed_reads'] == m['basecalled_reads']
assert m['passed_yield_bp'] + m['failed_yield_bp'] == m['total_yield_bp']
for key in ('channels', 'muxes', 'end_reasons'):
    assert sum(x['total_records'] for x in r[key]) == m['total_records']
    assert sum(x['total_yield_bp'] for x in r[key]) == m['total_yield_bp']
assert sum(x['yield_bp'] for x in r['time_bins']) == m['total_yield_bp']
assert r['time_bins'][-1]['cumulative_yield_bp'] == m['total_yield_bp']
assert sum(x['read_count'] for x in r['quality']['histogram']) == m['basecalled_reads']
assert sum(x['read_count'] for x in r['read_length_distribution']) == m['basecalled_reads']
assert sum(x['yield_bp'] for x in r['read_length_distribution']) == m['total_yield_bp']
print('Validated records:', m['total_records'])
PY
```

Repeat at least three times, retaining each timing separately. Compare report
bytes with `cmp`; there should be no run timestamps or ordering changes. Report
all measurements and distinguish cold-cache from warm-cache runs. Do not copy
the research input or identifying JSON report into version control.

## Reproducing the synthetic input

This creates approximately 1.60 GB on disk; keep it outside the repository:

```sh
python3 - <<'PY'
from pathlib import Path
n = 30_549_981
header = ('run_id\tchannel\tmux\tstart_time\tduration\tpasses_filtering\t'
          'sequence_length_template\tmean_qscore_template\tend_reason\n')
rows = []
for i in range(1000):
    flag = 'TRUE' if i % 2 else 'FALSE'
    reason = 'normal' if i % 3 else 'other'
    rows.append((f'scale-run\t{i%3000+1}\t{i%4+1}\t{(i*173)%86400}.5\t1.0\t'
                 f'{flag}\t{i*31+1}\t{(i*7)%50}.{i:03}\t{reason}\n').encode())
with Path('/tmp/poregauge-synthetic-scale.tsv').open('wb') as f:
    f.write(header.encode())
    block = b''.join(rows)
    for _ in range(n // 1000):
        f.write(block)
    f.write(b''.join(rows[:n % 1000]))
PY
```

Time the CLI with that path as input. Use a fresh timing process; exclude input
generation and compilation. The expected record count is 30,549,981, input size
is 1,599,749,860 bytes, and zero-length count is zero.

## HTML report maintenance (v0.4.1)

This measurement uses **fictional** data, not the private 28.2-million-record run.
`tests/fixtures/large_tables.rs` generates 20,000 unsorted records, 3,000 channels,
10,000 channel/mux pairs, 96 occupied time bins, three reasons, a zero-length-only
channel, and optional speed observations. Spatial maps are explicitly enabled.
Input: 1,542,325 bytes; SHA-256
`0dd41c69536062e895fdbafc528489b5e32a7e49fefd1bc81859503b99abba39`.

### Reproduction

Build v0.4.0 separately, for example in a temporary checkout, and retain its binary:

```sh
git worktree add --detach /tmp/poregauge-v040 v0.4.0
cargo build --manifest-path /tmp/poregauge-v040/Cargo.toml --release --locked
cargo build --release --locked
python3 tests/report_performance.py \
  --baseline-binary /tmp/poregauge-v040/target/release/poregauge --browser
```

The helper uses Python's standard library and `rustc` to run the **same generator**
as the Rust integration test. It writes ignored files under
`benchmark-results/html-performance/`: the TSV, before/after reports,
`measurements.json`, and optional `browser.html`. Omit `--baseline-binary` to
measure only the current build, or omit `--browser` for structural checks only.
JSON objects are compared after removing **only** `tool.version`; any other
change fails. The helper overwrites its own generated files, so preserve previous
measurements separately if needed.

Open `browser.html` directly via `file://`, press **Run checks**, and retain the
onscreen JSON/summary. It sequentially loads synthetic reports in `srcdoc` frames;
checks actual mounted rows, 25/50/100 sizes, sorting, substring search, empty
results, partial last pages, statuses, no-JS access, all 6,000 spatial cells, and
page overflow at 1440px/390px. After completion, enable **Emulate CSS print media**
in Chrome DevTools and press **Check print media**. Both detail-table containers
must be hidden and the omission notice visible, even with all 13,000 no-JS data
rows retained. Restore screen media afterward. This validates print CSS, not
printer-specific PDF pagination. No external resources or browser packages are
required. Sandbox script-blocking console messages in the no-JS cases are expected.

`cargo test` includes the small large-aggregation structural check (no table SVGs,
no external resources, all source rows preserved, bounded HTML size). When Node.js
is installed it also executes `tests/report_tables.cjs`, a dependency-free behavior
test including integer ordering above 2^53 and unavailable statistics. This can
also be run directly with `node tests/report_tables.cjs`; it uses a minimal DOM
stand-in, not a browser. Node is optional. Browser timings are manual and are not
CI performance gates; no full-run benchmark was added.

### Executed comparison

Measured on 2026-10-17, macOS arm64, release builds of v0.4.0 (`df78888`) and the
v0.4.1 maintenance implementation, Chrome 155.0.0.0. Values below come from one
final sequential browser pass with DevTools closed during timing; they are not
statistical throughput guarantees. The generator and both binaries were local.

| Structural measure | v0.4.0 | v0.4.1 |
| --- | ---: | ---: |
| HTML bytes | 8,258,004 | 7,098,116 |
| JSON bytes | 3,771,602 | 3,771,602 |
| Source elements (HTMLParser) | 185,760 | 165,755 |
| SVG roots | 10,026 | 23 |
| SVG rectangles | 27,491 | 7,485 |
| SVG table microbars | 10,003 | 0 |
| Source table rows, including headers/details | 13,468 | 13,468 |
| Mounted data rows: channel / channel × mux, JS default | 3,000 / 10,000 | 25 / 25 |
| All DOM elements after JS initialization (1440px) | 185,759 | 26,279 |
| All DOM table rows after JS initialization (1440px) | 13,468 | 518 |

HTML decreased **14.05%** on this fixture. All scientific JSON values/schema and
histogram definitions are identical; only the tool version differs. SVG roots
remaining after optimization are scientific charts/maps. Source row counts stay
unchanged for no-JS access. Source-parser and browser element counts differ
because JavaScript-enabled parsing treats `noscript` contents as text.

| Browser scenario | Load + two animation frames (ms) | Median synchronous handler (ms) | Maximum handler (ms) |
| --- | ---: | ---: | ---: |
| v0.4.0, JS, 1440px | 1,622.3 | 33.7 | 189.8 |
| v0.4.1, JS, 1440px | 1,435.6 | 1.5 | 59.5 |
| v0.4.1, JS, 390px | 995.8 | 1.4 | 60.2 |
| v0.4.1, no JS, 1440px | 2,307.6 | — | — |
| v0.4.1, no JS, 390px | 3,299.3 | — | — |

The median is the middle recorded duration across the scripted search/sort/page
operations in both tables; handler timing excludes assertions and animation-frame
waits. Load timing includes frame creation, parsing, script initialization, layout
and two frames, not just parsing. Caches, GC, frame placement and competing work
can change timings substantially; no universal load-time claim is made. At both
widths the JS report mounted 26,279 elements/518 table rows, with 25 data rows per
large table. No-JS retained 165,755 elements/13,468 table rows and all channel/pair
values. Print-media checks passed with those 13,000 data rows retained but both
detailed table containers omitted and the explicit notice visible.

All rows still arrive in HTML and are initially parsed; detached rows remain in
JavaScript memory. The improvement bounds mounted DOM and per-page updates, not
initial parsing or retained row storage. Full-list sorting and substring search
still scale with aggregated row count. These measurements do not remeasure or
predict the supplied real-report baseline of 9,052,704 HTML bytes; that private
report was not regenerated for this comparison.


## Complete-data MinION rendering (#14)

Measured on 2026-10-18, macOS arm64, Rust 1.98.1 release builds; baseline
`b1ed887` versus the full-count implementation. These are single executions,
not throughput guarantees: filesystem caches and competing work were uncontrolled.
The old binary samples ≤16 reads/channel; the new binary represents every
positive-length read. This is an information-coverage comparison, not a claim
of speed or file-size optimization. No private run was processed.

Reproduce with a separately retained baseline executable and the existing pinned
R environment (R 4.4.1, ggplot2 3.5.1, mgcv 1.9-1):

```sh
cargo build --release --locked
python3 tests/minion_visualization.py /path/to/pinned/minion_qc \
  --baseline /path/to/baseline-poregauge --rscript /path/to/Rscript \
  --render-reference
```

The standard-library helper generates fictional data, runs before/after CLI
analysis, verifies unchanged scientific JSON, executes actual pinned MinIONQC,
and checks independent full pixel counts. It writes ignored `measurements.json`,
reference captures, reports and optionally original R figures. Public inputs
stay in the pinned upstream checkout; routine CI needs no R or public downloads.
The extra ignored Rust probe measures the display-only phases on the source-file
population, irrespective of run-ID grouping, as R does. Normal CLI output still
splits known run IDs. `os.wait4` measures the specific CLI child's CPU and peak RSS
(macOS bytes, Linux KiB converted); wall time uses `perf_counter`.
